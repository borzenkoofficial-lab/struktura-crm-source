# СКОЛ CRM — проект единой ИИ-системы поиска заказов и компаний

Дата: 2026-11-02  
Статус: проект решения, ожидает подтверждения перед реализацией  
Базовая ветка: `feat/skol-ai-platform`

## 1. Цель

Превратить разрозненные поиски заказов, тендеров, клиентов и компаний в единую управляемую систему. Пользователь описывает коммерческую задачу обычным языком; ИИ строит план поиска, выбирает подключённые источники, запускает сбор, анализирует первичные страницы и документы, извлекает факты, проверяет соответствие профилю СКОЛ и сохраняет подтверждённые результаты в CRM.

ИИ является координатором и аналитическим слоем, но не подменяет источники данных. Факты должны поступать из API, открытых данных, разрешённых веб-страниц, подключённых аккаунтов или импортированных файлов. Модель не должна выдумывать компании, контакты, закупки, бюджеты, сроки и URL.

## 2. Цели

- Один поиск по заказам, компаниям, клиентам и закупкам из общей точки входа.
- ЕИС как отдельный приоритетный источник, а не набор поисковых запросов по домену.
- Подключаемые адаптеры для официальных API, открытых реестров, публичных сайтов, браузерных сценариев и файлов.
- ИИ-планирование поиска по услуге, региону, типу заказчика, бюджету, срокам, признакам актуальности и источникам.
- Глубокий анализ первичной страницы и доступной тендерной документации.
- Нормализация, дедупликация и связывание закупки, заказчика, компании и контактов.
- Проверяемое происхождение каждого факта: источник, URL, дата получения, фрагмент/страница документа и метод извлечения.
- Объяснимая оценка коммерческой пригодности для услуг СКОЛ: демонтаж, отделка/fit-out, фальшполы и другие направления, включённые в профиль.
- Повторный мониторинг изменений, статусов, сроков и новых документов.
- Сохранение ручной проверки и подтверждения перед созданием лида или изменением важных данных CRM.

## 3. Не-цели и запреты

- Не обещать доступ к закрытым данным или «всем источникам» без учётных данных, договора, API-разрешения или публичного доступа.
- Не обходить CAPTCHA, авторизацию, paywall, технические ограничения и запреты площадок.
- Не использовать браузерную автоматизацию как способ обхода ограничений API или условий площадок.
- Не отправлять заявки, делать ставки, писать заказчикам, покупать доступы и выполнять иные внешние действия без отдельного подтверждения пользователя.
- Не позволять LLM менять расчётные формулы, цены, сметы, финансовые и производственные записи.
- Не сохранять неподтверждённые предположения как факты.
- Не отправлять в модель лишние персональные данные, секреты, токены, пароли и документы без явной необходимости и контроля.

## 4. Рассмотренные подходы

### A. Только LLM + публичная веб-выдача

Дёшево и быстро, но покрытие зависит от индексации и HTML-парсеров поисковых систем. Не даёт надёжной работы с ЕИС, вложениями и закрытыми источниками.

### B. Только браузерный агент

Может читать страницы, где нет API, но ломается при изменении интерфейсов, авторизации, CAPTCHA и ограничениях. Дороже и менее надёжен для регулярного сбора.

### C. Комбинированная система: API + открытые данные + разрешённый браузер + ИИ

Выбран пользователем подход C. Он использует API/машиночитаемые данные там, где они существуют, браузерный сбор только для разрешённого публичного или авторизованного пользователем доступа, а ИИ — для планирования, извлечения, классификации, оценки и связывания результатов.

## 5. Предлагаемая архитектура

### 5.1. Единый Search Orchestrator

Единый сервис принимает задачу поиска и запускает жизненный цикл:

1. Разбирает запрос пользователя в структурированный Search Brief.
2. Уточняет недостающие параметры только когда они критичны.
3. Определяет тип сущности: заказ/закупка, организация, потенциальный клиент, контакт, генподрядчик или объект.
4. Выбирает источники по доступности, типу задачи, региону и настройкам пользователя.
5. Планирует запросы и параметры для каждого адаптера.
6. Запускает адаптеры с лимитами параллелизма, таймаутами, повторами и журналом ошибок.
7. Получает сырьевые документы и записи с provenance.
8. Нормализует и дедуплицирует данные.
9. Передаёт ограниченные выдержки и документы ИИ для извлечения структурированных фактов.
10. Проверяет факты по исходному материалу, вычисляет детерминированные признаки и отдельно получает ИИ-оценку.
11. Сохраняет кандидатов в staging/результаты поиска.
12. Показывает пользователю результаты, источники, уверенность, ошибки источников и действия для ручного подтверждения.
13. По расписанию повторяет мониторинг и фиксирует изменения.

ИИ не должен получать прямые полномочия на выполнение SQL, произвольный HTTP или вызов любых инструментов. Он выдаёт ограниченный план/структурированный ответ; приложение валидирует схему и исполняет только разрешённые действия через зарегистрированные адаптеры.

### 5.2. Контракт адаптера источника

Каждый адаптер реализует единый контракт:

- `id`, `displayName`, `sourceType`, `capabilities`, `authMode`.
- `healthCheck(config)` — доступность и состояние подключения.
- `validateConfig(config)` — проверка локальных настроек и credentials.
- `search(searchBrief, cursor, limits)` — выдача записей/документов.
- `fetchRecord(sourceId | url)` — подробности одной записи.
- `fetchDocuments(record)` — доступные вложения и документы.
- `normalize(raw)` — нормализация в общий формат.
- `getChanges(cursor | since)` — инкрементальная синхронизация, если источник поддерживает.
- `classifyError(error)` — понятный код ошибки: auth, forbidden, rate_limit, captcha, unavailable, parse_error, not_supported.

Адаптеры не должны знать о UI. Секреты хранятся локально через защищённое хранилище Electron и никогда не попадают в логи или промпты.

### 5.3. Источники и порядок подключения

1. **ЕИС / zakupki.gov.ru** — приоритет №1. Изучить и подключить доступные официальные открытые данные и документированные интерфейсы для 44-ФЗ и 223-ФЗ. Поддержать поиск извещений, планов, протоколов, контрактов, заказчиков, ИКЗ/реестровых номеров, сроков, НМЦК и вложений там, где поля реально доступны. Не считать сторонние API официальным интерфейсом ЕИС; любые внешние агрегаторы — отдельные опциональные провайдеры с явной стоимостью/ключом и маркировкой.
2. **Коммерческие тендерные площадки** — B2B-Center, Росэлторг, РТС-тендер, Фабрикант и другие источники по реестру. Для каждого проверить наличие официального API, открытой выдачи, требований авторизации и ограничений. Не предполагать доступность API заранее.
3. **Avito** — официальный API/доступ бизнес-аккаунта, если он покрывает нужные сценарии и пользователь имеет соответствующие права. Публичные страницы — только в разрешённых пределах. Если API не даёт поиск сторонних заказов, это должно быть явно показано как ограничение.
4. **Telegram** — официально подключённый бот/каналы, где бот является участником и получает сообщения, либо явно настроенный пользователем разрешённый клиентский доступ. Публичная веб-индексация — резервный источник, не полноценный Telegram-коннектор.
5. **Сайты заказчиков и компаний** — публичный веб-поиск + безопасный обход разрешённых страниц сайта, извлечение реквизитов/услуг/контактов с фиксацией источника и даты.
6. **Открытые реестры и каталоги** — реестры юридических лиц/контрагентов и открытые каталоги, если условия и API позволяют законное использование.
7. **Импорт файлов** — PDF, DOCX, XLSX, CSV, ZIP с тендерной документацией и списками компаний. Обработка должна идти через тот же pipeline, с сохранением исходного файла и ссылок на страницы/листы.

Каждый источник имеет собственный статус подключения: не настроен, подключён, ограничен, требует авторизации, временно недоступен, запрещён политикой источника. Ошибка одного адаптера не должна отменять результаты остальных.

## 6. Общие данные и доказательства

Для любой найденной записи хранить:

- тип сущности и внутренний ID;
- название и нормализованный идентификатор (ИНН/ОГРН/ИКЗ/номер закупки, если подтверждён);
- первоисточник, URL, внешний ID, дата публикации и дата получения;
- регион, заказчик/организация, предмет, категория работ;
- бюджет/НМЦК и валюта, только если они присутствуют в источнике;
- дата окончания подачи, статус и даты этапов, только если подтверждены;
- список документов и их SHA-256;
- извлечённые факты в виде {value, source_url, document_id, page_or_cell, quote, extraction_method, confidence};
- детерминированный сигнал и ИИ-оценку отдельно;
- объяснение релевантности и список причин исключения;
- историю изменений, последней проверки и статуса ручной проверки.

Дедупликация: сначала точные ключи источника и номера закупок, затем ИНН/ОГРН, нормализованные URL, затем вероятностное сопоставление названия/адреса. Вероятностное объединение не должно автоматически сливать разные организации без достаточных совпадений.

## 7. ИИ-слой

Набор ограниченных функций AnyModel:

- `planSearch` — JSON-план по заданию пользователя и доступным адаптерам.
- `extractProcurementFacts` — структурированные факты из страницы/документа с evidence.
- `classifyOpportunity` — подходит ли закупка профилю услуг и почему.
- `resolveOrganization` — сопоставление кандидатов компаний с доказательствами.
- `extractPublicContacts` — только опубликованные деловые контакты, с указанием страницы-источника.
- `summarizeChanges` — что изменилось между проверками.
- `draftNextAction` — предложить следующий шаг менеджеру, не отправляя ничего автоматически.

Каждый ответ валидируется JSON Schema. Любая ссылка, дата, сумма, ИНН и контакт должны быть проверены по источнику. Если доказательства нет, поле остаётся пустым/неизвестным. Промпты явно запрещают догадки и требуют возвращать evidence.

Ранжирование сочетает:
- жёсткие фильтры и детерминированные признаки (регион, услуга, статус, срок, диапазон бюджета);
- ИИ-релевантность и объяснение;
- полноту доказательств и свежесть;
- штраф за просроченную, закрытую или непроверяемую закупку.

ИИ-оценка не подменяет вычислимые поля и не может автоматически менять бизнес-статус.

## 8. Интерфейс CRM

Одна точка входа «Поиск ИИ» с вкладками/режимами: Заказы, ЕИС, Компании, Клиенты, Telegram, Avito, Все источники.

Поля задачи: свободное описание, услуги СКОЛ, регион/радиус, тип заказчика, период/сроки, бюджет (необязательно), выбранные источники, ограничения.

Панель источников показывает доступность, тип доступа, дату последней синхронизации, ошибки, требуемую настройку. В результатах показываются доказательства и источник, дата проверки, статус, оценка, причины, документы и кнопка открыть первоисточник.

Действия: сохранить в радар, создать лид, связать с существующей компанией, отметить нецелевым, поставить на мониторинг. Создание лида/слияние/изменение существующей карточки требует подтверждения пользователя.

## 9. Безопасность и конфиденциальность

- Все API-ключи и токены хранятся через Electron safeStorage; секреты не входят в Git, установщик, экспорт или диагностические логи.
- Пользователь явно включает каждый коннектор и видит требуемые права/тип данных.
- Минимизация передаваемого AnyModel контекста; персональные контакты передаются только для конкретной задачи извлечения и только при необходимости.
- Сырые документы по умолчанию обрабатываются локально до отправки ограниченных выдержек модели; настройка отправки документов должна быть явной.
- Учитывать robots.txt там, где он применим, условия площадок, лимиты запросов и требования законодательства РФ о персональных данных.
- Аудит действий: кто/когда запустил поиск, какие источники использовались, какие данные отправлялись в модель, какие записи были созданы/обновлены.

## 10. Этапы реализации

### Этап 1 — фундамент
- Аудит текущих поисковых потоков и схем БД.
- Ввести Search Orchestrator, контракт адаптера, единые типы SearchBrief/SearchResult/Evidence.
- Реестр источников и экран состояния подключения.
- Единый журнал поисковых запусков, ошибок, cursor и provenance.
- Миграции БД без потери текущих commercial_orders/prospects.
- Перевести текущий DuckDuckGo/Bing поиск и обход сайтов в адаптеры, не удаляя работающие сценарии.

### Этап 2 — ЕИС и тендерная документация
- Подключить проверенный источник данных ЕИС для 44-ФЗ/223-ФЗ.
- Получать извещения, заказчиков, статусы, сроки, НМЦК, документы.
- Скачивать доступные документы безопасно; PDF/DOCX/XLSX extraction.
- ИИ извлекает факты и ссылки на страницу/лист/ячейку.
- Повторная проверка статусов и дедлайнов.

### Этап 3 — коммерческие источники
- Подключить адаптеры коммерческих площадок по мере подтверждения доступов и технической возможности.
- Avito через официально разрешённый доступ/бизнес API, где он применим.
- Telegram через пользовательские разрешённые подключения и доступные каналы.
- Публичный веб и каталоги компаний.
- В UI честно отображать недоступные сценарии и причины.

### Этап 4 — единая база клиентов и компаний
- Связать заказы, организации, лиды, контакты и объекты.
- ИИ-анализ потенциальных клиентов и генподрядчиков.
- Поиск дублей и история взаимодействия.
- Подтверждение менеджером перед импортом/слиянием.

### Этап 5 — автоматический мониторинг
- Расписания, инкрементальная синхронизация, очереди/повторы, rate limits.
- Уведомления о новых подходящих закупках, изменениях и приближении сроков.
- Настройки частоты и лимитов, чтобы контролировать стоимость API и AnyModel.

## 11. Критерии приёмки

- Все существующие функции поиска компаний и заказов используют единый orchestrator; нет отдельной скрытой ветки, которая обходит реестр источников.
- Каждый источник имеет реальный адаптер или явно помечен как «не подключён / требует доступ / ограничен»; заглушки и фиктивные успешные ответы запрещены.
- Для ЕИС есть отдельный тестируемый адаптер с реальными контрактами запросов/ответов, а не только `site:zakupki.gov.ru` поисковые строки.
- Ошибка/тайм-аут одного источника не блокирует остальные; причины видны пользователю.
- Любой извлечённый факт имеет evidence; неподтверждённые поля не заполняются.
- Дубли выявляются без автоматического слияния сомнительных совпадений.
- Данные поиска сохраняются в существующей БД миграциями, старые карточки и статусы не теряются.
- API-ключи не попадают в логи, промпты, Git и экспорт.
- Тесты покрывают каждый адаптер через mocked contract tests, ошибки авторизации, rate limit, timeout, pagination, malformed response, dedupe и provenance.
- UI и Windows installer проходят CI.
- Live smoke test выполняется для каждого источника, для которого предоставлены credentials/доступ. Источники без доступа честно остаются не проверенными, а не объявляются рабочими.

## 12. Решения, оставленные исполнителю

- Выбор конкретного официального/лицензированного провайдера данных ЕИС после проверки актуальной документации, условий, лимитов и стоимости.
- Выбор технической реализации очереди и расписания, совместимой с текущим Electron/SQLite приложением.
- Поэтапный порядок коммерческих адаптеров на основании доступности API и фактической пользы.
- Не добавлять платные провайдеры, тарифы или инфраструктуру без отдельного согласования пользователя.

- Официальная страница государственных информационных систем Казначейства: https://mo.roskazna.gov.ru/gis/
